# AttendAI Research Experiment Configuration

## Purpose

This document freezes the configuration and evaluation rules for reproducible research experiments. It separates the application's current runtime configuration from the controlled settings required for scientific evaluation.

## A. Canonical recognition pipeline

| Component | Frozen research value |
|---|---|
| Face detection + embedding engine | InsightFace FaceAnalysis |
| InsightFace model | buffalo_l |
| Embedding | ArcFace-style InsightFace embedding |
| Similarity metric | Cosine similarity |
| Current runtime similarity threshold | 0.60 |
| Canonical attendance decision | Raw cosine similarity >= threshold |
| Image-quality assessment | Enabled |
| Quality score | 0.35 blur + 0.25 brightness + 0.30 size + 0.10 contrast |
| Quality-weighted confidence | similarity × (0.7 + 0.3 × quality) |
| Human verification | Enabled in application |
| Continual/adaptive encoding | Enabled in current application; DISABLED/FROZEN for baseline evaluation |

## B. Important implementation facts

These are implementation observations, not experimental performance claims.

1. The canonical attendance method obtains faces and embeddings through InsightFace `FaceAnalysis.get()`.
2. The `yolov8Detection` configuration block is legacy/misleading for the canonical attendance path. The configured YOLO detection confidence is not used as the face-detection filter inside the canonical `process_attendance_image()` method.
3. The current attendance identity decision is made using the raw best cosine similarity against the configured similarity threshold.
4. Quality-weighted confidence is calculated and returned as a confidence value, but it does **not** currently replace the raw-similarity threshold for the identity decision.
5. A successful attendance match can trigger continual-learning encoding updates when continual learning is enabled.
6. Enrollment currently stores one primary encoding per student in the canonical InsightFace service; attendance-derived adaptation can subsequently maintain multiple encodings.
7. The face-quality assessor currently uses implementation values of blur normalization at 500, optimal brightness 128, minimum face size 112, and contrast normalization at 60. The similarly named values in `app_settings.json` must not be assumed to control these implementation constants.
8. No numerical accuracy, F1, latency, FPS, or other performance value is considered research evidence until it is generated by the controlled experiment protocol.

## C. Baseline evaluation configuration

The baseline must be evaluated with:

- InsightFace `buffalo_l`
- cosine similarity
- a fixed threshold selected before evaluating the held-out test set
- fixed enrollment representations
- continual-learning/adaptive encoding updates disabled during the evaluation run
- no test image or test-derived encoding added to the enrollment representation before its prediction is scored
- identical preprocessing and detection settings across compared systems unless the experiment explicitly tests that component
- deterministic recording of model version, threshold, hardware, dataset split, and evaluation seed where applicable.

### Threshold calibration rule

The current application threshold of **0.60** is the starting configuration value, not a claimed optimal threshold.

For research evaluation, threshold calibration must be performed on a validation set that is disjoint from the final test set. The selected threshold must then remain fixed for the test evaluation.

## D. Controlled variants

### Variant B — Baseline

- InsightFace recognition
- raw cosine-similarity decision
- fixed enrollment encodings
- continual learning disabled
- no human correction during automated scoring

### Variant Q — Quality-aware reporting

- Same recognition decision as B
- Calculate and record face-quality score
- Report quality alongside similarity/confidence
- Do not change the identity decision rule

This isolates quality measurement from any claimed recognition improvement.

### Variant H — Human-in-the-loop

- Same automated recognition configuration as B
- Borderline cases routed to teacher verification according to a pre-defined rule
- Record suggested identity, similarity, quality, verification action, and final identity
- Human decisions are evaluated separately from automatic recognition

### Variant A — Adaptive encoding

- Same automated recognition configuration as B
- Enable attendance-derived encoding updates only after a prediction has been finalized
- Never update the representation set with a test sample before that sample is evaluated
- Record every encoding update and its source session

### Variant QHA — Full system

- Quality assessment
- Human verification
- controlled adaptive encoding
- all other parameters fixed

## E. Evaluation metrics

Primary recognition metrics:

- Accuracy
- Precision
- Recall
- F1-score
- False-positive rate
- False-negative rate

Attendance-level metrics:

- Correctly marked present
- Missed present students
- Incorrectly marked present students
- Session-level attendance errors

Operational metrics:

- Detection time
- Recognition time
- End-to-end latency
- FPS where applicable
- GPU/CPU utilization and memory where measured

## F. Data-split rule

The final test set must remain isolated from:

- enrollment images used to create the initial representation
- threshold calibration data
- adaptive encoding updates
- manual tuning decisions

Near-duplicate frames from the same source video must not be split across train/validation/test in a way that leaks identity-specific visual information.

## G. Reproducibility record

Every experiment run must record:

- Git commit SHA
- configuration version
- InsightFace model name/version
- hardware
- operating system/runtime environment
- dataset identifier
- number of students
- number of images/faces
- enrollment protocol
- validation/test split
- similarity threshold
- quality settings
- verification settings
- whether continual learning was enabled
- number of adaptive encoding updates
- evaluation metrics
- experiment timestamp

## H. Current application vs research configuration

The current `backend/data/app_settings.json` remains the application configuration. This document does not silently change that production configuration.

The research harness must explicitly override or isolate:

1. continual learning state;
2. threshold selection;
3. dataset split;
4. enrollment representation;
5. experiment logging;
6. adaptation timing.

This separation prevents application state from becoming hidden experimental state.
